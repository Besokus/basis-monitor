# 决策记录：实时指数价准确性与时效性平衡

日期：2026-04-08

## 背景

当前系统已经具备：

- `CTP` 期货实盘行情接入
- `XTP` 指数行情接入
- `CTP + XTP` 联合年化基差计算能力

但在联合计算落地后，需要明确一个关键策略：

- 当系统还没有收到 `XTP` 首笔指数价时，是否允许继续计算和告警
- 当 `XTP` 指数价已经 stale 时，是否允许继续用旧指数价计算和告警

这里的核心要求是：**年化基差告警必须尽量准确，同时兼顾系统时效性。**

## 结论

采用“**及时启动、严格告警**”策略：

1. 系统启动不强制等待 `XTP` 首包后才进入运行态
2. 但当 `XTP` 已启用时，只有在对应指数的实时价格已经到达且仍然新鲜时，才允许联合计算和年化基差告警
3. 如果 `XTP` 指数价尚未到达，暂停对应合约的联合计算和告警
4. 如果 `XTP` 指数价已经 stale，暂停对应合约的联合计算和告警
5. `CTP` 未开启或 `XTP` 未开启的单链路模式，仍允许沿用既有的昨收逻辑

## 选择理由

### 为什么不采用“严格双首包后才运行”

优点：

- 数据最严格

缺点：

- 启动时效性差
- `XTP` 柜台短时不稳定时会把整个系统直接阻断
- 不利于现场持续观察 `CTP` 主链和 `XTP` 支链

### 为什么不采用“XTP stale 也继续用旧指数价算”

优点：

- 结果连续输出

缺点：

- 告警准确性不可控
- 容易形成“系统看起来还在正常跑，但其实指数价已经过期”的隐性错误

## 最终权衡

最终采用：

- 启动阶段偏时效性
- 告警阶段偏准确性

也就是：

- 程序可以尽快进入运行状态
- 但一旦涉及年化基差告警，必须要求实时指数价可用且新鲜

## 实现落地

本次实现中已经落地为：

1. `XTP` 指数 tick 到达后，进入 `BasisMonitorService::OnIndexTick(...)` 缓存
2. `CTP` 期货 tick 到达后，由 `BasisMonitorService::OnTick(...)` 判断：
   - 是否还在等待实时指数价
   - 实时指数价是否已经 stale
3. 若不满足实时性要求，则：
   - 不产生 `BasisResult`
   - 不触发告警
   - 记录明确日志：
     - `WAITING_FOR_LIVE_INDEX`
     - `STALE_LIVE_INDEX`
