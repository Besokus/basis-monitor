# Basis Monitor 告警开发执行顺序清单

## 1. 当前目标
按最小可用闭环推进 `basis_monitor` 的告警能力，优先实现：
- 可持续计算年化基差
- 可识别负年化基差事件
- 可本地留痕
- 可向交易组发送企业微信通知

## 2. 建议执行顺序

### 阶段一：固化监控结果输出
目标：
- 先把“算出来了”沉淀成可复盘的数据，不急着先接外部通知

任务：
- [ ] 为每次有效计算生成结构化结果对象
- [ ] 将计算结果落盘到 `data/basis_results_YYYYMMDD.csv`
- [ ] 明确无效结果的处理方式
- [ ] 在运行日志中记录计算失败原因

本阶段完成标志：
- 能看到持续增长的计算结果文件
- 能按时间追溯某合约的年化基差变化

### 阶段二：实现告警事件状态机
目标：
- 将“负年化基差”从普通日志升级为真正的业务事件

任务：
- [ ] 建立 `entered_negative`
- [ ] 建立 `negative_reminder`
- [ ] 建立 `recovered`
- [ ] 为每个合约维护独立状态
- [ ] 支持连续 Tick 防抖
- [ ] 支持冷却时间

本阶段完成标志：
- 同一合约不会因每个 Tick 都为负而刷屏
- 恢复后再次变负能识别为新一轮事件

### 阶段三：落地告警事件日志
目标：
- 确保所有关键告警都有结构化留痕

任务：
- [ ] 将告警事件落盘到 `logs/alerts_YYYYMMDD.csv`
- [ ] 记录事件类型、分级、价格、年化基差率
- [ ] 记录通知是否发送成功
- [ ] 记录通知失败原因

本阶段完成标志：
- 任意一条告警都能在本地日志中查到完整上下文

### 阶段四：接入企业微信机器人
目标：
- 将本地告警事件转成交易组可见的通知

任务：
- [ ] 增加企业微信 Webhook 配置
- [ ] 增加启停开关
- [ ] 固定执行顺序：先写本地事件，再发企业微信
- [ ] 实现告警消息模板
- [ ] 实现恢复消息模板

本阶段完成标志：
- 首次进入负值时，交易组群里能收到清晰告警
- 恢复时，交易组群里能收到恢复通知

### 阶段五：补充失败处理与稳定性
目标：
- 避免企业微信异常影响主流程

任务：
- [ ] 增加发送超时控制
- [ ] 增加有限次数重试
- [ ] 增加发送失败日志
- [ ] 确保通知失败不阻塞行情接收
- [ ] 增加长时间无新 Tick 的健康提示

本阶段完成标志：
- 即使企业微信发送失败，监控主流程仍继续运行

### 阶段六：完善配置与文档
目标：
- 让系统具备可维护性和可交接性

任务：
- [ ] 将阈值、Webhook、冷却时间、confirm ticks 全部配置化
- [ ] 补充 README 中的配置说明
- [ ] 补充 README 中的运行方式
- [ ] 补充 README 中的告警规则说明
- [ ] 补充 README 中的日志文件说明

本阶段完成标志：
- 新接手的人无需读源码也能完成基本部署和配置

## 3. 每阶段建议产出

### 阶段一产出
- 计算结果 CSV 文件
- 对应单元测试或最小验证脚本

### 阶段二产出
- 告警状态机实现
- 状态切换测试

### 阶段三产出
- 告警事件 CSV 文件
- 事件字段说明

### 阶段四产出
- 企业微信通知模块
- 告警与恢复消息模板

### 阶段五产出
- 超时、重试、失败日志
- 健康检查日志

### 阶段六产出
- README
- 默认配置样例

## 4. 推荐开发节奏
- 第一步先完成阶段一到阶段三
  - 也就是先做到“本地闭环”
- 第二步再做阶段四
  - 接企业微信机器人
- 第三步最后补阶段五和阶段六
  - 做稳定性和交付文档

## 5. 开发优先级
- `P0`
  - 年化基差计算结果可持续输出
  - 负值事件识别
  - 本地事件留痕
- `P1`
  - 企业微信通知
  - 恢复通知
- `P2`
  - 重试、健康检查、完整 README

## 6. 建议的逐项验收顺序
1. 先验证计算结果文件是否正确生成
2. 再验证负值事件是否只触发一次
3. 再验证恢复事件是否正常产生
4. 再验证企业微信是否收到告警
5. 最后验证发送失败和长时间无新 Tick 的处理

## 7. 一句话执行原则
先完成“本地可计算、可判断、可留痕”，再完成“外部可通知、可恢复、可运维”。
