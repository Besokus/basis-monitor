# Basis Monitor 告警任务清单与开发规范

## 1. 目的
本文档用于固化 `basis_monitor` 后续开发中与“日内实时监控年化基差并通知交易组”相关的任务清单和开发规范，确保后续实现过程中对业务规则、日志留痕、企业微信通知、失败处理和验收标准有统一理解。

## 2. 业务目标
- 盘中持续接收股指期货实时行情。
- 基于期货价格、现货价格和合约到期日，实时计算年化基差。
- 当年化基差为负时，及时向交易组发出告警，辅助其评估是否执行加仓股指期货对冲。
- 对告警事件和发送结果进行留痕，便于盘中核查和事后复盘。

## 3. 计算规则

### 3.1 公式
- `basis = spot - future`
- `annual_rate = basis / spot * (365 / remaining_days) * 100`

### 3.2 输入项
- `spot`
  - 现货或指数价格
- `future`
  - 期货最新价
- `remaining_days`
  - 当前日期至合约到期日的自然日天数

### 3.3 异常输入处理
- 当 `remaining_days <= 0` 时，不参与正常监控计算，记为无效结果。
- 当 `spot <= 0` 时，不参与正常监控计算，记为无效结果。
- 对无效结果应记录到运行日志中，但不触发交易告警。

## 4. 告警业务规范

### 4.1 告警触发条件
- 当 `annual_rate < 0` 时，认为出现负年化基差。

### 4.2 事件类型
- `entered_negative`
  - 合约从非负状态进入负值状态
- `negative_reminder`
  - 合约持续处于负值状态，在冷却时间到达后发出的提醒
- `recovered`
  - 合约从负值状态恢复到非负状态
- `notification_failed`
  - 告警事件已产生，但外部通知发送失败

### 4.3 状态机要求
- 首次进入负值时，立即触发一次告警。
- 持续负值时，不得按每个 Tick 刷屏。
- 持续负值期间，只允许按冷却时间发送提醒。
- 从负值恢复为非负时，发送一次恢复通知。
- 恢复后如果再次进入负值，应当视为新的告警周期。

### 4.4 防抖与降噪
- 建议支持“连续 N 个 Tick 为负才触发”的防抖策略。
- 第一版推荐值：
  - `confirm_ticks = 2` 或 `3`
- 建议支持冷却时间。
- 第一版推荐值：
  - `cooldown_seconds = 300`

### 4.5 告警分级建议
- `info`
  - `0 > annual_rate >= -1%`
- `warning`
  - `-1% > annual_rate >= -3%`
- `critical`
  - `annual_rate < -3%`

分级阈值需配置化，允许交易组后续调整。

## 5. 日志与数据留痕规范

### 5.1 必须保留的日志类型
- 运行日志
  - 用于记录程序是否在线、是否收到行情、是否计算成功、是否发生异常
- 监控结果日志
  - 用于记录每次计算出的基差与年化基差结果
- 告警事件日志
  - 用于记录进入负值、提醒、恢复、发送成功与失败

### 5.2 建议输出文件
- `logs/monitor.log`
- `data/basis_results_YYYYMMDD.csv`
- `logs/alerts_YYYYMMDD.csv`

### 5.3 `basis_results_YYYYMMDD.csv` 建议字段
- `event_time`
- `instrument_id`
- `spot_price`
- `future_price`
- `basis`
- `remaining_days`
- `annual_rate`
- `is_valid`
- `source_update_time`

### 5.4 `alerts_YYYYMMDD.csv` 建议字段
- `event_time`
- `instrument_id`
- `event_type`
- `severity`
- `spot_price`
- `future_price`
- `basis`
- `remaining_days`
- `annual_rate`
- `cooldown_seconds`
- `notification_channel`
- `notification_status`
- `notification_error`

### 5.5 留痕原则
- 任何进入负值和恢复事件都必须有结构化记录。
- 企业微信发送成功或失败都必须有记录。
- 即使外部通知失败，本地事件日志也必须成功写入。

## 6. 企业微信通知规范

### 6.1 通知通道
- 第一阶段使用企业微信群机器人 Webhook。
- 第二阶段可考虑增加中转层，但不作为第一阶段必需项。

### 6.2 通知流程
1. 监控模块发现告警事件。
2. 先写本地告警事件日志。
3. 再调用企业微信机器人接口发送通知。
4. 将发送结果回写到事件日志。

### 6.3 通知失败处理
- 通知失败不得影响行情接收主流程。
- 通知失败必须记录详细错误原因。
- 应支持有限次数重试。
- 第一版建议：
  - `retry_times = 1` 到 `3`
  - 单次发送超时 `2` 到 `5` 秒

### 6.4 配置要求
以下内容必须配置化，不得硬编码在源码中：
- 企业微信 Webhook
- 是否启用企业微信通知
- 是否启用 `@` 提醒
- 冷却时间
- 连续负值确认 Tick 数
- 告警级别阈值
- 监控合约列表

### 6.5 消息内容要求
企业微信消息必须满足以下要求：
- 标题一眼说明问题
- 正文只展示交易决策最相关的信息
- 末尾给出动作提示，但不替代人工决策

### 6.6 建议告警文案模板
```text
[基差告警] IC2606 年化基差为负
时间：2026-03-27 10:15:08
现货：6300.00
期货：6312.40
基差：-12.40
剩余天数：84
年化基差率：-0.86%
建议：请交易组评估是否加仓股指期货对冲
```

### 6.7 建议恢复文案模板
```text
[基差恢复] IC2606 年化基差恢复非负
时间：2026-03-27 10:28:41
现货：6305.20
期货：6303.00
基差：2.20
剩余天数：84
年化基差率：0.15%
持续时长：13分33秒
```

## 7. 开发任务清单

- [ ] 建立告警状态机，支持 `entered_negative` 和 `recovered`。
- [ ] 增加冷却时间和连续 Tick 防抖配置。
- [ ] 增加 `basis_results_YYYYMMDD.csv` 落盘。
- [ ] 增加 `alerts_YYYYMMDD.csv` 落盘。
- [ ] 明确运行日志、监控结果日志、告警事件日志的职责边界。

### 7.2 第二阶段：企业微信通知闭环
- [ ] 增加企业微信群机器人配置项。

- [ ] 对发送结果进行成功/失败留痕。
- [ ] 增加通知失败重试与超时控制。

## 8. 验收标准

### 8.1 功能验收
- 程序能够持续接收真实行情并完成年化基差计算。
- 当某合约首次进入负年化基差时，能够生成一条本地告警事件。
- 当持续负值时，不会按每个 Tick 重复告警。
- 当恢复为非负时，能够生成一条恢复事件。
- 企业微信通知启用时，能够成功发送告警消息。
- 企业微信通知失败时，不影响监控主流程，并且本地有失败记录。

### 8.2 数据验收
- `basis_results_YYYYMMDD.csv` 能看到完整计算结果。
- `alerts_YYYYMMDD.csv` 能看到事件类型、分级和发送结果。
- 运行日志中可以区分：
  - 行情接收异常
  - 计算异常
  - 通知异常

### 8.3 运维验收
- 关键阈值和 Webhook 均可通过配置修改。
- 程序重启后仍能正常接收行情与继续告警。
- 日志文件和数据文件位置清晰、命名统一、便于复盘。

## 9. 开发约束
- 第一阶段不得引入自动下单逻辑。
- 第一阶段不得将交易决策自动化。
- 第一阶段应优先保证“可监控、可留痕、可通知”，而不是追求通知渠道复杂化。
- 告警模块不得阻塞行情接收主链路。
- 所有与通知有关的敏感配置应避免硬编码。

## 10. 后续建议
- 优先完成本地告警事件闭环，再接企业微信机器人。
- 在企业微信跑通后，再考虑短信、邮件或其他通知渠道。
- 当现货价源从本地配置升级为真实外部数据源时，应保持告警规则层不变，仅替换现货价提供方式。
